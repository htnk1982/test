# PDRM AUTO v3.3 — 自動安全判定版

## 基本方針

利用者はWAV/MP3のLUFSとTrue Peak上限だけを指定する。ピーク処理方式は手動選択しない。

各ピーク制御段は必ず次の順序で判定する。

1. **GAIN_ONLY** — 定数ゲインだけでLUFS/TPを満たせるなら、波形形状を変更しない。
2. **OPPO** — Gain-onlyではTPを超える場合、v3.2のオフライン波形最適化を試す。
3. **LIMITER_FALLBACK** — OPPOが `NotFeasible`（自然さゲート、変更量上限、有限探索上の不成立）を明示した場合だけ通常リミッターを使用する。
4. **STOP** — I/O異常、ファイル破損、非有限値、ソース変更、キャッシュ/整合性異常、キャンセル、コード/同梱資源異常等では、リミッターへフォールバックせずその曲を停止する。

「何らかのエラーが出たらリミッター」という設計ではない。フォールバック対象を `offline_peak_lab.NotFeasible` に限定している。

## 前段

HarmonicElasticity後の物理音声は **−14 LUFS / −2.5 dBTP** を目標にAUTO判定する。

Note-Subの観測判断は、HarmonicElasticity出力を**定数ゲインだけで−14 LUFSへ合わせた非公開の分析shadow**から行う。前段OPPOまたはリミッターが発動しても、その処理結果をNote-Subの音符・対象区間の判断教師にはしない。

分析shadowは公開音声ではないため、TP制限のためのリミッターを掛けない。実際の描画は安全確認済みの物理音声へ行う。

## 最終WAV / MP3

- WAV最終段も `GAIN_ONLY → OPPO → LIMITER_FALLBACK`。
- MP3は完成WAVから分岐し、MP3用内部WAVを同じAUTO順序で条件化してから320kbps MP3へ符号化する。
- 符号化後MP3を復号してLUFS/TPを再確認する。
- 前の方法で条件を満たした場合、後ろの方法は実行しない。

各曲の実行記録には `preparation_route`、`master_route`、`codec_routes` と、通常リミッターが実際に使用されたかを残す。

## GUI

GUIにはピーク処理方式の選択欄を置かない。表示する主設定は以下のみ。

- WAV LUFS-I
- WAV True Peak上限
- MP3 LUFS-I
- MP3 True Peak上限
- 既存のPDRM管理出力を退避して作り直すか

初期値はWAV −12 LUFS / −2 dBTP、MP3 −14 LUFS / −2 dBTP。

## 保存・クリーンアップ

元音源と同じフォルダの `processed` に同名WAV/MP3を保存する。公開後の整合性確認が完了してから、その曲のLOCALAPPDATA中間音声を削除する。通常失敗時も大容量中間音声を削除し、小さい診断だけ残す。強制中断時は同版の再開用チェックポイントを保持する。

v3.3開始時、同じsource hashに紐づくv3.0/v3.1/v3.2の旧作業キャッシュを回収する。無関係な他曲のキャッシュや `processed` 完成物は削除しない。

## 安全境界

- 通常リミッターはFFmpeg `alimiter` を使う既存の検証済みピーク処理。
- リミッターはGain-only/OPPOが先に成立した場合には呼ばれない。
- OPPO失敗理由を隠してリミッター成功と同一視しない。実行記録にフォールバック理由を残す。
- TPは4x/8x補間による数値推定であり、全D/A再生条件の保証ではない。
- 自動選択は知覚品質の絶対保証ではない。OPPOの自然さ保護ゲートを通せない場合、通常リミッターの方が安全に数値条件を満たすという優先順位である。

## 配布

ZIP全体を新しいフォルダへ展開し `PDRM_AUTO.exe` を起動する。Python、pip、別途FFmpegの導入は不要。EXE単体だけを取り出して配布しない。コード署名は付与していないため、組織のWindows保護ポリシーを無効化しない。
