# PDRM — EXE統合の残課題・実装契約 v1

日付：2026-09-09  
確認した基準commit：`9237e8e4f98f31318394592d06da401a49be9aea`  
状態：ソース確認に基づく統合設計。新DSP・新EXE・新たな音質試験の完了報告ではない。

## 1. 判断

次の開発単位を、独立LABの追加から、既存処理をつなぐ全曲の音楽的処理計画器へ変更する。処理器の種類を増やすことを主目標にしない。

完成条件は、元WAV/FLACの選択から、発音/成分の自動抽出、役割観測、問題診断、量決定、最終WAV/MP3の検査、同名保存、曲単位クリーンアップまで、開発者による発音時刻の手入力なしで完走すること。

低域の新制御は旧Note-Subの後に追加せず、その判断・生成経路を置換する。HE・HFTC・OPPOの採用済みDSP本体は初回統合で変更しない。バグや実装上の単位不整合まで保存するという意味ではない。

## 2. ソースにより確認した不足

| 箇所 | 現状 | 統合に必要なもの |
|---|---|---|
| `event_decay_v39.Event` | 時刻、anchor、対象帯域、関連帯域、role/familyを呼出側が供給 | 任意の全曲から候補と根拠を自動生成する入口 |
| 相対減衰の時間条件 | 最短0.8秒、最長8秒。anchorとtailの文脈が必要 | 短い低音の発音を別経路で扱う。対象外を正常と呼ばない |
| スペクトル解析 | 12kHz、4096サンプル窓、240サンプルhop | 約341msの窓と20ms更新を区別。hopを発音検出精度とみなさない |
| `event_decay_v39.calibrate()` | 同じrole/family/相対帯域配置で、4独立群以上の局所正例が必要 | 既存の弱い役割レビューから実際に利用可能な校正への橋渡し |
| `event_groove_v37.process_event()` | 手渡しイベントの同一基音を補強。量は固定LAB予算 | 全曲イベント抽出、実曲の量校正、物理枝との由来照合 |
| `auto_conditioned_v34.run()` | 旧Note-Subの解析・生成・強度選択を呼ぶ | 新計画器への差替え。旧生成器との二重実行禁止 |
| `natural_finish_v34._runtime()` | ロック下で共有モジュール参照を一時差替え | 初回は曲ごとの直列処理。共有状態差替えをさらに増やさない |
| 検証 | Boundary39に173件のソフトウェア試験と18合成ケースの記録 | 実モデル推論と実曲自動処理、最終AUTO、実EXEを結んだ試験 |

0.8秒未満の発音を扱わないのは現在の相対減衰LABの仕様上の範囲であり、全パイプラインが短音非対応と断定するものではない。ただしこの分岐一つを、短音を含む全低域の制御器として出荷することはできない。

## 3. 最初の統合候補の範囲

含める：KEEP、過大な低域ヒットの整理、局所的な低域占有の整理、支持された相対減衰の修正、校正が成立した同一基音補強、既存HE/HFTC/最終AUTO、保存・後始末。

初回の出荷条件から外す：新規octave-down、存在する基音が不明な合成、全楽器の完全な意味理解、新しい中高域エキサイター、HFTC全面改修、巨大な汎用嗜好モデル、10倍高速化、GPU/NPU必須化。

同一基音補強の量校正が未完了なら搭載済みと称さない。修復のみの限定評価版を作る場合は、その範囲を明示し、従来の有効な補強まで無言で失わせない。一般公開版と研究用評価版の完成条件を混同しない。

## 4. 二つの信号経路と同一性

```text
元ファイル
├─ 原音解析 → 全曲の候補抽出 → 必要区間の役割観測 → 音楽イベント台帳
└─ HE → 既存AUTO前段 → 新低域coordinator → 既存HFTC
                         ↓
                共通予算で差分を描画
                         ↓
              既存AUTO最終WAV → MP3枝 → 保存後検査
                         ↓
                 原子的な公開 → 曲単位掃除
```

原音解析は位置・音程・役割の証拠を提供する。適用量・干渉・余裕はHE/AUTO後の実音声から再測定する。非線形な前処理後は、同じLUFSでも局所波形が同じではない。

原音と物理枝でhashが異なることは正常。hash照合を外したり、観測のhashを差し替えたりして無理に接続しない。

必要なインターフェース：
- `SourceIdentity`：元ファイルhash、復号PCM識別子、レート、長さ、チャンネル。
- `RenderSnapshot`：物理音声hash、親SourceIdentity、処理段階、config/code hash。
- `TimeMap`：原レートの整数フレーム、SRC比、補償遅延、端点丸め規則。
- `Evidence`：観測器/モデル版、支持時間、役割、不一致、音程と対応の根拠。
- `MusicalPlan`：症状、対象、操作、許容量、保護対象、校正版、未対応理由。
- `Outcome`：技術的成功と、改善/未解消/保留を別々に持つ。

## 5. 全曲イベント抽出と時間設計

短時間の立ち上がり検出と、十分な周期を必要とする低域の音程・倍音分析を分ける。単一の約341ms窓に両方の役割を任せない。音程用の長窓と発音境界用の短窓を同一の原音時計へ対応づける。

関連成分の候補には、共通の立ち上がり、音程軌跡、倍音関係、包絡の追随、役割の安定、他音との競合を使う。同じ役割・同時発音だけで同じ音符と断定しない。非調和な打撃音を無理に倍音系列へ当てはめない。

拍情報は文脈に使い、発音位置は動かさない。長い音を短くすることも、すべてのアタックを強くすることも目的にしない。短くても過大なヒットは別分岐で扱う。

先に軽量な全曲解析を行い、操作候補を含む区間を十分な前後文脈つきで観測する。近接区間はまとめ、窓端の証拠不足には重なりを持たせる。候補の取りこぼしを別に検査し、未観測を解析済みと数えない。

## 6. 校正が成立しない問題への設計

現行v39は厳密な局所正例を要求する。既存の全曲役割コメントはそのままでは局所正例条件を満たさない。この不足を隠して、合成参照を本人の嗜好で校正済みとしてはならない。

既存レビューを使う校正系は三層で設計する。
1. 原音内の同種イベント。ただし全曲に同じ欠点がある場合は正解とみなさない。
2. 役割・発音形態・相対音程が近い参照群の弱い事前情報。
3. 明示的な局所評価が存在する場合、その強い保護/修正条件。

役割コメントから自動抽出した区間は弱いラベルのまま保持する。空欄を正例にせず、ある楽器への好評を別の楽器に転用しない。弱い情報を使う校正器は別の版・ラベル種別とし、v39の厳密条件を満たしたように装わない。

暫定境界は、原版/故障コピーと既知の実曲の対照で検証する。しきい値はすべて学習済みの自然さの真理ではなく、実測により改訂する設計値である。

追加の大量な局所ラベル付けを利用者に要求することを標準の成立条件にしない。一方、資料にない主観判断を機械的に捏造して不足を埋めない。

同じ曲群が開発に使用されている点を保持し、同一コーパスのleave-one-outを独立した最終評価と呼ばない。原版とその故障コピーは同じグループに置く。

## 7. 複数処理の適用量を一つにまとめる

ヒット制御、占有率制御、相対減衰、基音補強を順番に最大適用しない。すべて同じ物理snapshotを参照して候補を作り、共通の変更予算で裁定する。

同じ時間・帯域で、一つの制御器が削り、別の制御器が不足と見て足す自己相殺を禁止する。優先順位は発音禁止/保護条件、既存の過剰修正、不足が残る場合の同一基音補強。

減算マスクは共通の時間・周波数表現で重複を裁定する。複数の1.5dB処理を無言で足し上げない。ただしマスクの上限だけでは実音の局所量・位相干渉を保証できず、描画後の混合音を再測定する。

同じ入力snapshotから有限個の候補と無加工を作り、修正目標を満たし、保護条件を破らない中で最小の変更を選ぶ。候補が未達なら予算内の代替を検討し、最大処理を成功と呼ばない。

## 8. 最終AUTOとの相互作用

HE/HFTC/OPPOのコードが同じでも、低域修正によってその後のピークやLUFS、制御量は変わる。コード凍結と、完成音の質感保持は別の試験とする。

比較は同じ原入力・同じHE/前段から、低域修正の有無を分岐し、HFTC→AUTO→MP3まで通す。既知の誤生成を含む旧Note-Sub結果を無条件の正解にしない。

GAIN_ONLY/OPPO/LIMITERが実際に動いたこと、理由、最終LUFS/TP、符号化後の結果を記録する。低域の役割推定失敗を通常リミッターへ回して修復成功と呼ばない。数値目標は利用者の指定を維持し、勝手に下げない。

最終出力で対象の実改善と、非対象への影響を別に確認する。スペクトル整理、アタック、声、曲末、ステレオ、原音不変を一つの平均スコアで相殺しない。今回の主観資料で15kHz超が承認済みとは扱わず、新しい高域改造へ範囲を広げない。

## 9. モデルの配布条件と依存環境

研究に使用したHDEMUCS_HIGH_MUSDBは、TorchAudio公式資料でMUSDB-HQ訓練セットによる学習が明記されている。Demucs READMEはMITを表示する一方、作者のIssue #327コメントは重みをMIT対象外・科学目的と説明している。

本資料は個別の利用の法的結論ではない。しかし当該checkpointの配信用利用と再配布が確認済みとも扱えない。特定の重みと用途について根拠を確認するか、許諾が明確な重みへ差し替え、同じ観測タスクを再評価する。利用者による別ダウンロードや重み形式変換を、許諾の代用品にしない。

モデルmanifestには配布元、hash、前処理/推論版、条件の根拠、許容用途、対応機能を持たせる。モデル変更は観測仕様の変更として校正と回帰を伴わせる。一般利用向けの配布物に未確認の研究重みを混ぜない。

TorchAudioはmaintenance phaseに入っている。「最新版なら動く」という依存解決にせず、Python/Torch/TorchAudio/NumPy/SciPy/FFmpeg/PyInstallerとモデルの組をWindowsで固定する。既存I/Oはできるだけ維持し、依存更新と音質改修を同時に混ぜない。

## 10. Windows・SSD・実行時間

配布は、従来同様に起動EXE一つが見えるフォルダ型ZIPを基本とする。Python/pip/手動ステム書出しを利用者に要求しない。権利確認済みモデルは管理された場所へ置き、曲処理中に無断ダウンロードしない。

GUIとworkerを分離し、モデルはworker内で再利用する。初回出荷は曲ごとの直列処理とする。multiprocessingを使う場合はGUI生成前のfreeze_support、子プロセス回収、キャンセル、FFmpeg終了を実EXEで検査する。

10倍高速化は再開しない。ただし新しいステム観測を含む処理時間は測定する。旧版で許容された速度を新経路でも維持できると、未測定で宣言しない。

全4ステム×全曲をWAVに溜めない。観測波形は特徴を取り出したら解放し、必要な小さな特徴と計画だけを保存する。メモリも全曲のfloat64配列を何本も持つ構成にしない。

モデル/設定、job作業領域、完成音、旧出力backupを分離する。
- 成功：完成WAV/MP3と記録を照合・公開した後、その曲が所有する中間物を削除。
- 通常失敗/キャンセル：大きな中間音を削除し、小さな原因記録を保持。
- 強制終了：次回にlock/所有manifestを確認し、resumeまたはそのjobだけの掃除。
- 完成音backupはキャッシュではない。作業領域の掃除で消さない。

開始前にメモリ・作業先・最終保存先・backup分の容量/権限を検査し、途中でも空き容量を監視する。モデル不在を音響的な不成立と混同して旧生成器へ戻さない。

## 11. 完了と保留を分ける

| 状態 | 意味 | 処理 |
|---|---|---|
| KEEP | 支持された範囲でその操作は不要 | 無加工。全音質正常とは断定しない |
| CORRECTED | 検証可能な修正目標を達成 | 対象・操作・数値を記録 |
| PARTIAL | 予算内で改善したが未達 | 改善と未解消を分けて表示 |
| ABSTAIN | 役割/関連付け/校正の支持不足 | 根拠のない生成をしない。良好率に含めない |
| TECHNICAL_FAILURE | I/O、破損、非有限値、hash不整合など | 中止。リミッターで隠さない |
| CANCELLED | 利用者の中止 | worker回収と所有領域の掃除 |

新機能を要求する通常モードでモデルが欠落・破損・用途未確認なら開始前に停止する。解析なしの縮退結果を自動で新方式成功にしない。安全な音量整合だけを別機能として残す場合は範囲を明示する。

GUIはWAV/MP3のLUFS/TP、ファイル選択、進捗、キャンセル、既存出力退避を中心に保つ。役割ごとの閾値やモデル選定を利用者へ押し付けない。

## 12. 実装順と完了条件

| 順序 | 作業 | 終了条件 |
|---|---|---|
| 1 | source/physical/time-mapとcoordinatorの枠 | 旧Note-Sub二重呼出しなし。全KEEPなら新低域差分0 |
| 2 | 全曲イベント抽出、観測scheduler、関連付け | 手入力時刻なし。短音/曲端/境界で証拠と音がずれない |
| 3 | 弱いレビューの校正経路と操作別量決定 | 好例保存と負例修復を両立。常時バイパスで合格しない |
| 4 | 共通予算とAUTO/MP3結合 | 二重補正なし。実動作するOPPO/limiterを含む完成音で確認 |
| 5 | Windows評価EXE | Python未導入・ネット遮断・通常権限で実モデルを含む一曲完走 |
| 6 | バッチ/保存/掃除/再開/最終聴感 | 容量累積や破綻なし。内部比較を絞り必要な聴感判断だけ残す |

モデル用途・再配布とWindows依存の確認は順序1と並行する。完成間際に発見して設計全体を戻す形にしない。

試験は、(1)単体契約、(2)原版/故障コピー、(3)実曲の自動処理、(4)実EXE運用の四層。173件は過去の単体・合成検証の成果であり、実曲の神経観測やEXE試験の代わりではない。

利用者へ毎回の全曲再試聴、大量JSON、局所ラベルの全面追記を依頼しない。既存素材で内部比較を絞り、判断を変える最小限の聴感確認だけを最終工程に残す。

## 13. 今回の状態

この変更は統合設計文書のみ。新しいDSP実行、神経推論、全曲再処理、自動試験、新EXEの成功は主張しない。ローカルcontainer/Pythonは応答せず、根拠確認は接続repoと提供仕様、公式資料で行った。音源・レビュー・参照プロファイル・重みを今回のcommitへ追加していない。

次に実装する中心は新しいLAB効果ではなく、全曲のMusicalPlanを生成して旧低域入口を置換するcoordinator。ここまでの成果を一曲の経路にまとめる。

検討の三視点：音響側は好ましい発音/質感の保持、推定側は弱いラベルと不確かさの保存、運用側はモデル条件と容量/公開整合を要求する。共通方針は統合器へ進むこと。残る論点はモデル、校正、実音での適量。現時点で利用者に新たに要求する判断はない。
