# PDRM 音符追従型サブベース補完 — 実験版 v0.2.1

## 目的

採用済みC（HarmonicElasticity）を変更せず、Cを入力として音符追従型の低域追加だけを隔離実験する。

v0.2系では、v0.1.1のイベント監査で判明した責務混同を解消し、次を分離した。

1. 音符追跡
2. 生成先周波数の選択
3. 追加量の判定
4. 波形描画・位相積分

v0.2.1ではさらに、前後が同じ生成先で中央1フレームだけ推定先が飛ぶ場合に限り、そのフレームを無音のままtrackingだけ橋渡しする。未知区間、休符、明示された境界は延長しない。

本番 `pdrm_engine` / `pdrm_runtime` / `pdrm_operator_lab` は変更しない。採用CへHarmonicElasticityを再実行しない。通信、モデルダウンロード、pip実行もしない。

これは研究試作であり、実曲で音質が改善したことをまだ意味しない。次の工程は追加監査ではなく、採用Cそのものを使った実曲回帰である。

## 実行前提

- 既存の `PDRM_Local_Render_Engine_v1` と `.venv` が動作済みであること。
- Round9で実際に採用したjobの `manifest.json` が残っていること。
- manifestが `PDRM-v0.6-Round9-HarmonicLoudness-exp1` であること。
- `LAB_INTERNAL/blind_mapping.json` で C = `HarmonicElasticity` であること。
- `RENDERS/HarmonicElasticity.wav` のSHA-256が次と一致すること。

`ee2df798b8a3096bba078968c0db9e953769a42924f717de02f9107936e4e7d1`

一致しない音源は処理しない。MP3や別マスターを代用しない。

## 配布物の置き方

CI成果物 `PDRM_Note_Sub_Lab_AddOn.zip` の中身を、既存の `PDRM_Local_Render_Engine_v1` フォルダへ上書きコピーする。

最低限、次の4ファイルが同じフォルダに存在する状態にする。

- `note_sub_lab.py` — v0.1.1互換の隔離runtime。production runtimeではない。
- `note_sub_lab_v02.py` — v0.2系の音符追跡・生成先・追加量・描画。
- `note_sub_launch.py` — v0.2系を起動する診断ランチャー。
- `note_sub_lab.cmd` — Windows起動用。

`.venv` や本番DSPを作り直さない。

## 実曲Cをレンダリングする

1. `note_sub_lab.cmd` をダブルクリックする。
2. ファイル選択画面で、今回採用したRound9 jobの `manifest.json` を選ぶ。
3. その後は処理を完了まで進める。途中でselftest、doctor、追加監査を挟まない。
4. 正常終了したら、表示された `RESULT` フォルダを開く。

原則の出力先：

`%LOCALAPPDATA%\PDRM_Local_Render_Engine_v1\note_sub_lab\sub_...\RESULT`

## 今回見る成果物

### 聴取に使う

- `PDRM_Note_Sub_BLIND_MP3.zip`
  - `LISTEN_A_320kbps.mp3`
  - `LISTEN_B_320kbps.mp3`

先に `REVEAL_AFTER_LISTENING.txt` を開かない。

A/Bを同じ再生条件で聴き、まず次のどれかだけ決める。

- Aがよい
- Bがよい
- 差が小さく決められない
- 追加版に明確な破綻を感じる

判断時に、適用率やイベント数を見て音を選ばない。

### 問題切り分けに使う

- `CONTROL_C.wav` — 入力Cのコピー。
- `SUB_AUGMENTED.wav` — v0.2系実験出力。
- `DELTA_SUB_FLOAT.wav` — 実際に足した低域だけ。

実曲レビューの主軸は以下。

1. 誤った音程の低域が出ていないか。
2. 本当の休符へ低音を足していないか。
3. 同一の持続音が短い膨らみに分断されていないか。
4. キックの瞬間だけ不自然に膨らんでいないか。
5. 低域の連続性が改善したか。
6. 採用Cの「疲れにくい・うるさくない」という長所を壊していないか。

## JSONの扱い

`SUB_REPORT.json` と `NOTE_EVENTS.json` は、再現性・内部記録・必要時の原因追跡のために生成する。ただし、**正常な実曲回帰を進めるためにユーザーへ追加JSON提出を要求しない。**

次のいずれかが起きた場合だけ、原因箇所に必要な既存記録を参照する。

- 明確な誤音
- 休符への追加
- 不自然な分断
- レンダリング失敗
- 数値ゲートによる想定外の無処理

問題が起きた場合は、可能性だけで監査項目を増やさず、その失敗を再現する最小の音声ケースまたは最小のコード回帰試験へ落とす。

## v0.2系の設計境界

### 音符追跡

追加量が0でも、観測上同じ音符なら追跡を継続する。`KEEP` を音符終了とみなさない。一方、十分な観測がない未知区間へ前の音を自動延長しない。

前後が同じ生成先で、中央の1フレームだけ生成先が不連続に飛び、かつ境界・再アタックの証拠がない場合は、その中央フレームのraw観測を保存したままtracking targetだけを前後から橋渡しする。その20msは追加量を0にするため、文脈補正によって誤音を鳴らさない。2フレーム以上続く変化や境界付き変化は橋渡ししない。

### 生成先

推定f0と生成先を別管理する。推定f0が1オクターブ切り替わっても、生成先が同じで音符継続の観測がある場合、それだけで包絡・位相を再開始しない。本当の再アタック、休符、別音符は接続しない。

### 追加量

既存target成分、既存sub RMS、desired level、ピーク余裕を使い、音符内で追加量を変える。「足さない」と「音符が終わった」を別状態として保持する。

### 波形描画

同一tracked noteでは位相積分を継続する。追加量0の内部区間でも内部位相は保持できるが、その区間に未知の音を生成することとは分ける。固定60msフェードを短音へ無条件適用しない。

## 工学ゲート

既存labの隔離runtimeを用いて、次を保持する。

- 入力Cのhash検証
- 入力・production側の非変更
- 8秒単位の分析／レンダリングcheckpoint
- 中断後の再開
- 既存結果の上書き禁止
- 全曲 -14 LUFS matching
- PCM TP推定 -1.5 dBTP以下
- MP3復号後 TP推定 -1.0 dBTP以下
- 追加レイヤー110Hz以上のエネルギー漏れゲート
- 追加量scaleの有限候補 `1.0 / 0.5 / 0.25`

これらの数値ゲート通過は、聴感品質の合格を意味しない。

## 状態の意味

- `RENDERED_EXPERIMENT_NOT_QUALITY_APPROVAL`：実験出力を生成し、工学ゲートを通過。次は聴取。
- `NO_ELIGIBLE_ADDITION`：候補が得られずCを保持。低域十分の証明ではない。
- `NO_ADDITION_WITHIN_GATES`：候補はあるが工学ゲート内では追加しない。
- `FAILED_NOT_PUBLISHED`：成果物として公開していない。闇雲に再試行しない。

## 現時点の回帰試験

v0.1.1の既存33試験を残し、v0.2系の回帰を追加している。

- f0と生成先の分離
- f0のオクターブ切替で同一target noteを再開始しない
- 音符内の追加量0でtracking/phaseを終了しない
- 同音再アタックと実休符を分離する
- 既存低域十分でもtrackingは継続する
- 既知ベース + キック + 和音 + 高域打撃の混合音回帰
- v0.2 full runでCとproduction runtimeを変更しない
- 前後が同じ場合の単発target外れだけを無音bridgeする
- 2フレーム続くpitch changeをbridgeしない
- boundary付き外れをbridgeしない

GitHub Actionsでは Ubuntu/Python 3.12、Windows/Python 3.12、Windows/Python 3.14 を対象とする。v0.2.1のCIでは合計43試験を通すことを実曲実行前のhard gateとする。

## 次の終了条件

次の状態まで進めば、v0.2系の最初の実曲回帰は終了とする。

1. 採用Cからv0.2系のブラインドA/Bが生成できた。
2. ユーザーが音だけでA/B/差なし/破綻のいずれかを判断した。
3. reveal後、追加版が勝てば次の不足品質へ進む。
4. 追加版が負けるか破綻した場合は、聞こえた具体的失敗だけを最小回帰試験へ戻す。

**同じ監査資料を増やすことは終了条件ではない。実曲での状態差分を作ることが次の工程である。**
