# PDRM OPPO v3.2 — 長文脈ピーク再配置＋曲ごと自動クリーンアップ

日付: 2026-09-06

## v3.1からの変更

実曲バッチで、v3.1の局所Rescueが `Rescue local naturalness gate failed: {'residual': False, 'energy': False}` で停止した。これは、旧42.67ms窓の中だけで必要なピーク修正を完結させようとし、変更量が局所ゲートを越えたケースである。

v3.2では、**v0.1で選好された旧ソルバーを先に必ず実行**する。旧ソルバーが成功する窓は、その結果を変更しない。旧ソルバーが `Residual budget cannot fit this peak` で止まる窓だけをいったん未修正のまま全曲へ重ね、全曲の仮出力を作る。その後、失敗箇所の前後を含む **128 / 256 / 512 / 1024ms** の文脈へ順に広げ、必要最小の加算差分を最適化する。

したがって、v3.1の局所ゲートを単に緩めた版ではない。短い窓で無理に帳尻を合わせるのをやめ、オフライン処理の利点である長い文脈を実際の波形変更範囲として使う。

## 長文脈Rescueの保護条件

- 指定ピーク上限へ入れるための最低修正量を計算する。
- 瞬間ピークの60%を超える書換えが必要なら停止する。
- 文脈端12msは差分を0へ滑らかに戻す。必要ピークが端に来る文脈は採用しない。
- 元のデジタル無音サンプルは変更しない。
- 元の周波数包絡、静かな時間、左右方向から外れる差分を従来と同系統の二次コストで高く評価する。
- 文脈ごとに差分RMS、エネルギー、20ms包絡P95/最大、M/S変化を検査する。
- 128msで成立しなければ256→512→1024msへ広げる。ゲートそのものは段階ごとに緩めない。
- 全曲合成後は従来どおり、全曲残差、帯域レベル、20ms包絡、M/S、無音保持を再検査する。
- 通常リミッター、クリッパー、目標LUFSの自動引下げ、旧前段への自動切替はしない。

これらは工学的な保護条件であり、不可聴性や疲れにくさを自動証明するものではない。

## 前段

標準は引き続き **一定ゲインのみ（前段リミッターなし）**。

`HarmonicElasticity → 一定ゲイン準備 → Note-Sub → HFTC → OPPO v3.2`

比較時と同じ旧前段ピーク整形は、GUIで処理前に明示選択する互換モードとして残す。失敗後の自動フォールバックには使わない。

## WAV / MP3設定

GUIでWAVとMP3それぞれのLUFS-IとTrue Peak上限を指定できる。初期値はWAV −12 LUFS / −2 dBTP、MP3 −14 LUFS / −2 dBTP。

MP3は完成WAVから作り、MP3側に追加ピーク処理が必要な場合も通常リミッターではなくOPPOを使う。復号後にLUFS/TP/長さを検査する。

## 出力

```text
元フォルダ/
├─ 曲名.wav
└─ processed/
   ├─ 曲名.wav
   ├─ 曲名.mp3
   └─ .pdrm/
```

元音源は変更しない。設定変更時の管理済み旧出力バックアップも維持する。

## SSD容量対策

v3.2は1曲ごとに処理を閉じる。

- **成功**: `processed` のWAV/MP3と管理記録を検証した後、その曲のHarmonic、Note-Sub、HFTC、OPPOチャンク、PCM24、MP3検査用WAV等の作業ファイルを `%LOCALAPPDATA%\PDRM_Local_Render_Engine_v1\oppo_finish_v32` から削除する。
- **通常の処理失敗**: 大きなWAV/MP3中間ファイルを削除し、原因を再現するための小さいJSON診断だけ `diagnostics` に残す。
- **再実行**: 成功済み曲は元フォルダの `processed/.pdrm` 記録で照合してスキップできるため、大容量キャッシュを残す必要はない。
- **途中中断**: 同じv3.2の未完了キャッシュは次回開始前には保持し、途中再開できる。正常な失敗として1曲が閉じた場合は削除する。
- **旧v3.0/v3.1の同じ入力のキャッシュ**: v3.2でその曲を選んだ時点で、同じ入力ハッシュに紐づく古い作業物を先に削除する。

`processed/.pdrm` の小さい管理JSONや、失敗診断JSONは保持する。元音源、完成WAV/MP3、手動編集物はクリーンアップ対象にしない。

## 配布

Windows x64向けPyInstallerフォルダ配布。ZIP全体を展開し `PDRM_OPPO.exe` を起動する。EXEだけを抜き出さない。Python/FFmpegの追加インストール不要。コード署名なし。

## 検証境界

v0.1選好済みカーネル、v3.0ストリーム、v3.1救済コードは変更しない。v3.2は別モジュールとして追加する。旧ソルバー成功トラックのサンプル完全一致、長文脈Rescue、無音・モノ/逆相・境界、途中再開、入力非破壊、作業キャッシュ削除、失敗時診断保持を回帰する。

利用者PC上の25曲そのものはCIにないため、ビルドだけで25曲全件成功は主張しない。今回ログで確認されたv3.1の失敗構造を解消する実装として、実バッチで最終適用範囲を確認する。
